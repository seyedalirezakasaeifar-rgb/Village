## Observations and intended distinctions

1. **Issued payloads survive model-only rollback.** A valid first save holds its IndexedDB promise. A refused purchase then debits cash before its null dereference; the next save writes that partial payload immediately to localStorage and queues it for IndexedDB. The test deliberately restores the original model and RNG; its full archive is exactly equal to the pre-action archive. Releasing the first write still issues the partial queued envelope, and localStorage retains the partial state. Work trace: good local write, good IDB issue, bad local write, bad IDB issue. Two bad external payloads survive the exact model restoration. Same timeline/epoch; chronology has advanced. This is a witness of why an already-issued external effect cannot be repaired by G-only rollback, not a suggested rollback implementation.
2. **Unserialized startup deferral behaves differently.** When save waits for store readiness and the model is restored before serialization, it serializes the restored committed model exactly once. This ordinary latest-state deferral is safe in the controlled case; it must not be confused with an already captured/issued payload.
3. **Following UI commands are distinct actions.** MessageChannel tasks execute refused construction, the real borrow button, the real save button, and the export entrypoint in order. Borrow applies exactly once (+$5000 debt), with no dropped task. The earlier $12250 working-capital loss remains; local save and the Android bridge spy expose the partial financial state. This is a browser event-task sequence on the synchronous baseline, not a cooperative or native gesture-queue certification.
4. **Feedback is not an economic commit.** The current global error route emits a runtime-issue toast. The later save emits “Village saved on this device.” and really did persist the partial payload: this is not a false storage acknowledgment. The forbidden behavior is the partial upstream purchase and its durability/export. Candidate checks must not be “fixed” by merely hiding notifications or silently dropping the subsequent save/borrow/export action. A capacity refusal may issue truthful feedback immediately.
5. **Ordinary decision metadata is separate.** An actual protected-loan-ledger refusal changes no finance, RNG or identities but adds 195 persistent bytes of creditDecision metadata. That is intended model information, subject to reserved archive headroom. The positive financial-conservation test does not mistake this for a partial loan advance. A candidate may instead decline without adding metadata if its documented capacity policy requires that.
