# Service access uses current household membership

`serviceAccess()` caches a road-catchment allocation across UI and simulation reads. Its population aggregate had been clamped to `G.stats.population`, which is published after parts of the daily pipeline and can still describe the previous tick while household membership already reflects arrivals or births. If an early caller populated the cache during that window, the old result could survive after `recompute()` updated the public statistic. Archive load invalidates the road graph, so the same household snapshot was then recomputed using the newer aggregate. That made health/school reach and civic training diverge after an otherwise exact save/load continuation.

The service allocator now calculates its denominator from the same living resident rows used to form household demand. It no longer couples a current access allocation to a potentially stale published statistic. No purchase/payroll formula, wage or budget threshold is changed. With a consistent published census, independent matched tests retain identical allocations, policy outlooks and complete state after purchases. Correcting a genuinely stale allocation changes reach/training results and can change later outcomes; blanket trajectory neutrality is not claimed.

The regression fixture deliberately adds 18 ordinary test residents to each household while leaving the published population at 169 until the next recompute. The live household total is 1,375. Both public service access calculations now immediately report the live total and internally consistent coverage. The existing retail proposal review then completes its actual UI review, archive/continue sequence, and exact save comparison without mismatch in service coverage, training progress, cash, or RNG. This adversarial population jump is test-only; it is not a claim that the game creates residents instantly.
