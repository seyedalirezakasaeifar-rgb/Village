# Native economy-tier renderer QA

Source commit `29dd12af7d4aac6b22efcfe1cec1e2d59aff2c1f`; canonical assembled `assets/game.js` SHA-256 `b277816a34f6de3ce3448a459a47630a61ed5e980e5e02f6bae2dcd135c8bd58`. Scratch-only manifest/package and launch query used package `org.townledger.vale.qaeconomy29dd`, URL `?cityArt=webgl&cityQuality=economy&cityBadge=1`. APK SHA-256 `f1d592a094793ecaed28d433b02a72ecd435c27c04338574665bf8b4b96cffcc`.

On API 30 / WebView 83.0.4103.120 (x86_64 software emulator, SwiftShader), the economy renderer initialized and the actual scene showed the synthetic 169-resident town. Runtime reported 21 draw calls and 18,114 triangles. Real Android touches opened the Town Hall inspector, panned and zoomed the map, and paused/resumed simulation. While paused the WebGL frame count stayed fixed for 10 seconds. Camera gestures preserved the complete save hash. Controlled `WEBGL_lose_context` triggered the visible `Canvas fallback · 3D released`; the WebGL canvas was removed and the original Canvas remained. The paused save hash was identical across context loss.

The actual Graphics quality selector was exercised with Android input. **Performance** stored `quality=low`; after `am force-stop` and relaunch, the Welcome page still showed Continue and local storage still held `low` before town loading. The QA launch URL included `cityQuality=economy`, which overrides renderer selection only. **Balanced** was selected separately under a Canvas-only QA launch (`?cityBadge=1`): both the visible selector and local storage read `balanced`. After another force-stop/relaunch, before Continue, local storage remained `balanced` and the 411,257-byte town envelope remained present. Tapping Continue restored Day 9 with the visual snapshot quality still `balanced`. The Canvas-only wrapper was used to isolate preference persistence from SwiftShader scene initialization; it is not the released wrapper.

To diagnose the Welcome return, a temporary QA wrapper build added lifecycle and WebView page callbacks; it changed no game source. The exact same process PID `26675` logged `onPause`, `onDestroy(finishing=false)`, `onCreate(savedState=true, swdp=450)`, and `onResume` when the emulator changed from 640×360 to 800×450. Restoring 640×360 produced the same destroy/recreate sequence with `savedState=true` and `swdp=360`, followed by a fresh `pageStarted/pageFinished` for the launch URL. The process did not die. This confirms an Android Activity recreation for the size configuration, followed by WebView reload to Welcome; it was not a process death. The manifest handles `orientation|keyboardHidden|screenSize` but not `smallestScreenSize`, so the system recreates the Activity when the smallest-width bucket changes. `townledger-v6` remained present, Continue was visible, and the saved town loaded on tap. The emulator display was restored to 640×360. See the sanitized [QA lifecycle log](LIFECYCLE-LOG.txt) and [pre-resize screenshot](economy29dd-before-instrument-resize.png).

A portrait user-rotation request at the original 640×360 display size stayed at rotation 0 because the app is explicitly `screenOrientation=landscape`; system rotation settings were restored afterward. This is the existing app behavior. The actual 3D resize/layout check remains incomplete. The renderer module took minutes to initialize on this software emulator and interactions were slow. These results do not establish physical-device performance.

All images depict a synthetic QA town. No raw state snapshots, APKs, signing material, user saves or personal data are included. No source edits were made for this QA build.
